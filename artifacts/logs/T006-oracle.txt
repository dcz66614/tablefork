## 4. Judgement calls made in THIS oracle (spec does not pin these down)
O1. Unknown attributes on any element -> INVALID_RAGGED_GRID (strict
    subset reading of spec 3.1; J1 buckets out-of-subset ELEMENTS, and
    this oracle extends the bucket to out-of-subset attributes).
    NOTE: no Golden fixture exercises this; it is a recorded divergence
    risk for T011 / final review, not a silently settled fact.
O2. A span reaching past the last DOM row, or across a thead/tbody
    boundary -> INVALID_SPAN.
O3. Error precedence: OVER_SIZE(bytes) -> parse errors in document order
    -> OVER_SIZE(rows/DOM cells) -> INVALID_SPAN / INVALID_GRID_OVERLAP
    during placement -> OVER_SIZE(cols) -> INVALID_RAGGED_GRID.
O4. Grid rows follow DOM order of <tr>; bare <tr> under <table> is an
    implicit tbody row; implicit tbody + explicit <tbody> in one table
    is INVALID_RAGGED_GRID (two tbody groups).
O5. Entity decoding: only ';'-terminated references; fixed table of
    common named entities + numeric refs; unknown names stay literal;
    U+00A0 is never folded or trimmed; only ASCII whitespace folds and
    is trimmed at the edges.
O6. alternativeHtml uses this oracle's own canonical serialisation
    (attribute order rowspan, colspan, scope). The spec does not pin a
    serialisation, so the alternativeHtml STRING is a known open point
    for cross-implementation comparison; the B graph (b_cells +
    b_slotOwner) is the comparable content. See also section 8, item 1.

### G33 — pipe / backslash escaping (order-sensitive), ORIGIN_EMPTY
Input cells (raw text): "a|b", "c\d", "e\|f", "g" (2x2, no merges).
Escape rule (spec 5.1): backslash FIRST, then pipe. "a|b" -> "a\|b";
"c\d" -> "c\\d" (one backslash becomes two); "e\|f": backslash pass ->
"e\\|f", pipe pass -> "e\\\|f" (three backslashes + escaped pipe).
F (both strategies, no merges): "| a\|b | c\\d |\n| --- | --- |\n|
e\\\|f | g |\n". Handover carries the RAW values (a|b, c\d, e\|f, g).
Witness both: NO_WITNESS_FOUND ("no merged cells").

### G36 — whitespace folding + trim, ORIGIN_EMPTY
Input (literal newlines/tabs inside cells): cell (0,0) raw
"  多   空\n格\t表  "; (0,1) "第二"; (1,0) "\n前后\n"; (1,1) "  x  ".
Normalisation (spec 3.1): consecutive ASCII whitespace folds to one
U+0020, edges trimmed -> "多 空 格 表", "第二", "前后", "x".
F both = "| 多 空 格 表 | 第二 |\n| --- | --- |\n| 前后 | x |\n".
Witness both: NO_WITNESS_FOUND ("no merged cells").

### G42 — overlap rejection, ORIGIN_EMPTY
Input: <table><tbody><tr><td>A</td><td rowspan="2">B</td></tr>
<tr><td colspan="2">C</td></tr></tbody></table>
Placement: row0: A at (0,0); B at (0,1) spanning rows 0-1, col 1.
Row1: first free column is 0 (col 1 held by B); C at (1,0) colspan=2
covers (1,0) and (1,1); (1,1) is already occupied by B ->
INVALID_GRID_OVERLAP. Expected error code: INVALID_GRID_OVERLAP.
(No slotOwner / cells / F / witness: the input is rejected.)

## 8. Discrepancies found during comparison, and how each was resolved
All three were investigated by hand against the written spec; in each
case the hand derivation (not the program) was the side in error, except
item 1 which was a serialisation-order convention. Nothing was silently
adjusted to match a program output.

1. alternativeHtml attribute order (G30, found on the first 12-seed run,
   11/12). Hand-written B HTML used `<th scope="row" rowspan="2">`;
   reference.py serialises rowspan, colspan, scope in that order
   (`<th rowspan="2" scope="row">`). The spec does not pin an attribute
   order, so this is a convention choice, not a semantic difference.
   Resolution: adopted the serializer's order (rowspan, colspan, scope)
   as the oracle's canonical order (recorded as O6) and rewrote the two
   affected altHtml strings (G30, both strategies). A blanket
   search-replace also touched six INPUT html strings (G17/G21/G24/G30/
   G31/G40 — attribute order in an input is semantically irrelevant to
   parsing, but the change made the fixtures disagree with the golden
   inputs); those six were reverted to the originally hand-written
   order, and the /tmp fixtures were regenerated. Lesson recorded: never
   blanket-replace across input and output fields.
2. G16 handover incomplete (found on the first 48/48 run: "handover:
   length differs (expected 3, got 5)"). My hand list had only the three
   tbody td slots and missed the two thead td slots (0,0) and (0,1),
   whose owner is a td ("非标题"). Spec 5.4 says "对每个 td 占用的槽位"
   with no section qualifier, so the oracle's five lines are correct.
   Resolution: hand list corrected to five lines (two thead td lines
   added). This was a genuine hand error, caught by the oracle.
3. G28 B construction — phantom continuation cell (found on the first
   48/48 run, after item 1 was fixed). My hand-written B for G28 listed
   an 8th cell "" at (3,0) and altHtml `<tr><td></td><td>d</td></tr>`
   for the last row. By hand re-derivation: the split candidate is c00
   (上, rows 0-1); the OTHER rowspan cell 下 (rows 2-3) is untouched,
   so slot (3,0) is still owned by 下 and is NOT a DOM cell — row 3 has
   only the single DOM cell d. Resolution: b_cells corrected to 7 cells
   (d is c06 at (3,1)), b_slotOwner row 3 corrected to [c04, c06],
   altHtml last row corrected to `<tr><td>d</td></tr>` for both
   strategies, and the hash filler re-run (b_graph_sha256 follows from
   the corrected b_cells). Genuine hand error, caught by the oracle.
   I also re-audited every other fixture's B for the same error class
   (untouched rowspan cell whose continuation slot I might have written
   as a DOM cell): G09/G24/G25/G29/G30/G31 all check out — their B rows
   emit only DOM cells, with continuations correctly omitted.

### 勘误 (A)：facts 定 TD-only——build_facts 改为只对 td 占用的槽位出记录

- 原行为：build_facts 对每个槽都出一条（含 th 槽；G02 为 4 条
  [c00..c03]）；且本 Oracle 自身的 handover 已是 TD 过滤
  （handover_lines 只取 role == "TD" 的槽），facts 与 handover
  内部不一致。
- 改后：build_facts 跳过 role != "TD" 的槽（与 handover_lines 已用的
  同一 TD 过滤一致）；G02 的 facts 为 2 条 [c02, c03]，与 handover
  行数一致。
- 理由（规格原文）：项目书 §5.4“对每个 td 占用的槽位，稳定序列化”；
  交接稿由 facts 生成，facts 含 th 槽会让交接稿出现标题格行，与 §5.4
  矛盾。
- 连带：oracle/golden_expected.json 各条 facts 数组删 th 槽条目
  （共 99 条，24 条 fixtures；其余字段一字未动，handover 本来就是
  TD-only，未动）。指纹字段无需重填：a_graph_sha256 /
  b_graph_sha256 / markdown_sha256 的输入分别是 cells+slotOwner、
  B 图、F 字符串，均不含 facts——已用独立脚本（/tmp 脚本，不提交）
  按 T006 §2 的办法重算全部 212 个哈希字段（160 个 a 图/ F 哈希 +
  52 个 B 图哈希），改前改后均为 0 不匹配。

### 勘误 (B)：未知属性忽略——解析器不再拒绝未知属性

- 原行为（本文 §4 O1）：任何不在 _CELL_ATTRS 里的属性报
  INVALID_RAGGED_GRID；`<td data-x>`、`<table class>`、`<td style>`
  均被拒。O1 原文（§4）自此作废，以本附录为准。
- 改后：删 _check_cell_attrs 的未知属性拒绝循环与 table / thead /
  tbody / caption / tr 的表级属性拒绝；未知属性解析后丢弃。
  保留：rowspan/colspan 解析与 1–8 校验（INVALID_SPAN）、scope 取值
  校验（row/col 合格；rowgroup/colgroup/非法值报
  UNSUPPORTED_HEADER_SEMANTICS）、headers 属性报
  UNSUPPORTED_HEADER_SEMANTICS。其他解析/网格/标题/F/见证逻辑未动。
- 理由（规格原文）：项目书 §3.1“有效标签”只限标签
  （table/thead/tbody/tr/th/td/caption），未给属性设限；有语义的
  属性只有 rowspan/colspan/scope/headers（其中 headers 与
  scope=rowgroup/colgroup 按 §3.1 报 UNSUPPORTED_HEADER_SEMANTICS）；
  T003 的 J1 管的是超集元素，Oracle 把它扩展到属性是自己的选择
  （见本文 §4 O1 原文）；§3.1“格式处理”明说格式是丢弃不是拒绝；
  拒 class/style/data-* 会让工具拒掉几乎所有真实粘贴表，与工具用途
  相悖；属性不渲染，无安全角度。
- 验收：O1 三例在 TS 与 Oracle 两侧均接受，headers 仍两侧同码拒绝
  （见 artifacts/logs/T011-FIX-01.txt §5）；`npm run oracle` 仍 48/48。
