--------------------------------------------------------------------------------
任务的前提是“只改 notes 文字，ZIP 不变”：它假定只有 REVIEW_INDEX.md
变了才需重打 ZIP，且 REVIEW_INDEX.md 不记录清单 SHA 故 ZIP 不变。
核查证明该前提不成立——改模板的文件本身就在发布包内：

 1. scripts/verify_release.mjs 在清单 192 文件内（旧哈希
    4819b6ca…/29950 B），且在 source ZIP 的 192 条目内；它还以全文块
    嵌在 review/REVIEW_PACK_05.md（块头 SHA 与清单一致，由 verify
    检查 (d) 核对），并以 SHA+行数列在 review/REVIEW_INDEX.md 第 31 行。
    改模板一字即改该文件字节 → 清单的该文件条目、PACK_05 的该块、
    INDEX 的该行全部过期；只改 notes 不动它们，verify:release 的
    “清单哈希与工作树一致”与“分卷块 SHA 与清单一致”两项必 FAIL。
 2. 故 source ZIP 必须重打（同 192 文件集，内容换入新脚本/新卷/新索引），
    其 SHA 由 3d023f3b… 变为 d7b38e55…（见下）。dist ZIP 不含该脚本，
    全新构建重打后逐字节一致，SHA 不变 e0a2ce5e…。
 3. packaged_from_head 不能维持 b7e1023：新 ZIP 的树 ≠ B 的树（3 文件
    不同：脚本、PACK_05、INDEX）。维持旧值会使 notes 的等式
    “ZIP = packaged_from_head 的树 + 机械重生成文件”成假话。执行时把
    脚本修正先单独提交为 E1，再以 E1 为打包时 HEAD 生成清单与 ZIP：
    packaged_from_head = 5b37530…（E1）；机械重生成文件 = 2 个
    （REVIEW_PACK_05.md 与 REVIEW_INDEX.md，由分卷生成器在打包时重生成；
    脚本已在 E1 的树内，不算重生成）。notes 的等式因此为真。
 4. notes 的冻结提交引用由 task_handoffs/P029-REFREEZE.json 改为
    task_handoffs/P029-REFREEZE-NOTES-FIX.json：前者 result_commit 是
    原冻结提交 ca8bed6，新 ZIP 的树 ≠ ca8bed6 的树（3 文件不同），沿用
    它会重犯同类误标；新冻结提交是 E2，由本次交接 JSON 的 result_commit
    指明。REVIEW_INDEX.md 本身不记录清单 SHA（grep 清单 SHA 为 0），
    但它记录脚本 SHA 与 PACK_05 的 SHA，故仍须联动更新（5 行，见下）。
