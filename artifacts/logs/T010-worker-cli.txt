## 7. 裁决小节（§7：规格未钉死的点）
- J-T010-1（fixture 策略选择）：四个 fixture 的 input.strategy 统一为
  ORIGIN_EMPTY（默认策略）。REPEAT_VALUE 由 UI 覆盖：T009 已在真实浏览器
  里验证四个预设 × 两种策略（TFK-A/B 两种策略下仍为碰撞，TFK-C/D 不变），
  本卡不重复造第二套 fixture；CLI 对任一策略的 fixture 都能跑（validate
  接受两个策略值），T011 的 Golden 会覆盖两种策略。
- J-T010-2（Worker 为何让步一个 macrotask）：analyze() 体内没有 await，
  调用后同步完成；若处理器在收到 ANALYZE 后立即执行，RESULT 会在同一
  microtask 检查点发出，抢在随后到达的 CANCEL / 新 ANALYZE 之前，使取消
  与竞态守卫在真实浏览器里永远观测不到。因此处理器先
  `await new Promise(r => setTimeout(r, 0))` 再执行 analyze()；让步后
  同一任务里接连 post 的 CANCEL / ANALYZE 先被处理，旧 job 在执行后被
  版本号守卫或取消集合压住（浏览器实测 §5 证实）。代价约 1 个定时器
  tick；让步后还会二次确认（generation / latestJobId / cancelled）才
  执行 analyze()，省一次无用计算。主线程的“只采纳最新 jobId”仍是
  T013 的接线责任；Worker 侧守卫是纵深防御，不是替代。
- J-T010-3（CLI 退出码口径）：0 成功；1 表格被 analyze() 拒绝（stderr
  为枚举错误码 + message，不写输出文件）；2 CLI 层失败（参数缺失/未知
  参数、输入文件读不到、JSON 解析失败、fixture 结构不符；stderr 为
  `ERROR CLI_USAGE: …`，不是枚举码——因为这不是表格错误而是调用错误）；
  --help 打印用法到 stdout，退出 0。TFK-D 的 exit 1 是预期行为（表格
  本身被拒绝），不是 CLI 故障。
- J-T010-4（CANCEL 的版本号口径）：取消只在被取消的 job 正是当前最新
  job 时才递增版本号；取消一个已被取代的旧 job 只登记进 cancelled 集，
  绝不碰版本号——否则会误杀最新 job 的结果（单元测试第 11 项钉死）。
  同理，ANALYZE 同一 jobId 复用时会清除该 jobId 的旧取消记录（新分析
  不应被上一轮的 CANCEL 压住）。
- J-T010-5（cli/ 不在 typecheck 覆盖内）：T001 冻结的 tsconfig.json
  include 只有 src/、vite.config.ts、playwright.config.ts，所以
  `npm run typecheck`（tsc --noEmit）不检查 cli/analyze.ts。本卡未改
  tsconfig（不在输出清单内）；改用同样 strict 的独立 tsc 命令对
  cli/analyze.ts 与 src/worker/tablefork.worker.ts 各跑一次，均为
